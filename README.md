# Web Guidelines

Scope: web interfaces. Dimensions = CSS px unless specified; CSS px ≠ device pixels; native points ≠ CSS `pt`. `M` = requirement; `D` = default, justified exceptions allowed; `O` = optional treatment. These are project rules, not a claim that every preference is a standard. Accessibility, native behavior, and data integrity take precedence over visual preference. CSS/HTML snippets specify browser behavior; stack-specific implementation is in §16. References identify standards and API behavior, not a prescribed visual identity.

**M · Safety invariant:** Never bypass safety: no `any`/`Any`, unsafe casts/assertions, non-null/definite-assignment `!`, `@ts-ignore`, swallowed exceptions, ambiguous truthiness, shared mutable state/defaults, mutation of the iterated collection or its elements, exact floating-point equality, or unvalidated boundary input. Strict checks remain enabled; types stay precise. Fix the model, validation, or control flow, not the diagnostic. Applies to application code, tests, examples, and tooling; no visual, performance, or brevity exception.

## 1. Targets, touch, zoom

- **M · Hit areas:** pointer targets ≥24×24; touch-first controls ≥44×44; visual glyph may be smaller; activation areas cannot overlap neighbors. [WCAG 2.5.8][targets] AA = 24×24 with defined exceptions; [2.5.5][targets-enhanced] AAA = 44×44. Inline links are not automatically square buttons. Using the spacing exception ⇒ centered 24px-diameter circles cannot intersect another target or another undersized target’s circle.
- **M · Target geometry:** `min-inline-size:44px;min-block-size:44px` establishes the touch-control baseline; padding can enlarge a smaller visible icon without enlarging its artwork. Expanded hit regions remain inside the control’s usable area and never intercept adjacent controls. Touch capability can coexist with a mouse; a narrow-screen or primary-pointer check alone does not identify every touch user.
- **M · Mobile text/zoom:** editable controls’ computed font-size ≥16px, e.g. `font-size:max(1rem,16px)`; viewport = `<meta name="viewport" content="width=device-width,initial-scale=1">`; no `user-scalable=no` or zoom-limiting `maximum-scale`. This font-size baseline avoids focus auto-zoom in affected mobile browsers without disabling user zoom. Desktop single-purpose input ⇒ contextual autofocus may help if it does not skip necessary context; touch/mobile ⇒ no automatic keyboard opening unless essential.
- **M · Touch behavior:** normal controls ⇒ `touch-action:manipulation`; hover styling ⇒ `@media(hover:hover)`. Custom gesture surface ⇒ least restrictive policy, e.g. `pan-y pinch-zoom`; `touch-action:none` only where essential, never globally. Tap highlight remains visible or has equivalent pressed feedback; transparent `-webkit-tap-highlight-color` requires replacement. Drag/swipe/path/pinch actions ⇒ click/tap and keyboard alternatives unless the gesture is essential.
- **M · Event geometry:** the full visually interactive area activates the control; list-row spacing belongs inside hit-area padding, not dead gaps; checkbox/radio label activates the control. Decoration ⇒ `pointer-events:none`; input adornments sit inside the padded input footprint and pass clicks through to focus it. Independently interactive suffixes remain real, named buttons. `user-select:none` is limited to control chrome/active dragging, never blanket body text. Drag preview/inactive layers may be `inert`; focused draggable and usable drop targets may not.

## 2. Semantics, focus, keyboard

- **M · Native first:** action ⇒ `<button>`; navigation ⇒ `<a href>` or router link rendering an anchor; tabular data ⇒ `<table>`; field ⇒ native input plus label. Navigation preserves middle-click, Cmd/Ctrl-click, context menus, copying URLs. No clickable `<div>` substitutes. Non-submit buttons explicitly use `type="button"`; submit buttons use `type="submit"`. Every control exposes its actual name, role, state, and value; visible text belongs in its accessible name; icon-only buttons require names; decorative icons ⇒ `aria-hidden="true"`.
- **M · Structure:** meaningful document title per route/state; coherent `h1`–`h6` hierarchy; landmarks; working “Skip to content” link that reaches the main region, e.g. `<a href="#main">Skip to content</a>` plus `<main id="main" tabindex="-1">`. Visually omitted labels still have accessible equivalents. Accessibility tree reflects useful content, not implementation wrappers or database-schema names.
- **M · Focus:** logical DOM/tab order; no positive `tabindex`; all keyboard focus visible and unobscured, including under sticky chrome. Default ring example: `:focus-visible{outline:2px solid var(--focus);outline-offset:2px}`; grouped control ⇒ `:focus-within`. Focus color meets required contrast. Never remove outline without an equivalent indicator. `box-shadow` alone is insufficient in forced-colors, where shadows can disappear; retain an outline/system-color fallback.
- **M · Keyboard patterns:** ordinary controls use normal Tab order; composite menus/listboxes/tabs/grids use their [WAI-ARIA APG][apg] arrow-key, Home/End, Enter/Space, selection, and roving-focus behavior. Not every list becomes an arrow-key widget. Shortcuts respect platform conventions, non-QWERTY layouts, assistive technology, and system reservations; display the platform’s modifier key, e.g. ⌘ or Ctrl, rather than a universal hard-coded shortcut. Delete-selected-item shortcut, e.g. Cmd+Backspace, never intercepts text editing and always has a visible alternative plus recovery.
- **M · [Modal focus][dialog]:** open ⇒ meaningful initial focus inside; Tab/Shift+Tab contained; background actually inert; explicit close/cancel; Escape when appropriate; close ⇒ focus returns to invoker or logical successor. `aria-modal="true"` only for genuinely modal behavior. Irreversible action ⇒ safe initial focus; focus location ≠ Return-key default. Nonmodal popovers do not inherit modal traps.

## 3. Fields, autofill, input behavior

- **M · Native submission:** related fields belong in `<form>` with a real submit button; native Enter submission remains intact. `<textarea>` Enter inserts newline; optional Cmd/Ctrl+Enter submits. Custom keyboard handlers ignore composing input, e.g. `event.isComposing`; no global “submit only the final field” handler.
- **M · Labels:** each field has an associated `<label for>`/`id` or equivalent accessible association; label click focuses/toggles correctly. Placeholder ≠ label. Units, requirements, format examples, and errors are programmatically associated, e.g. `aria-describedby="email-help email-error"`; invalid state ⇒ `aria-invalid="true"` when warranted.
- **M · Input semantics:** meaningful `name`, suitable `type`, appropriate `inputmode`; numeric identifier ≠ arithmetic number. Postal code/account number ⇒ text plus suitable keyboard hint, preserving leading zeros; email ⇒ `type="email"`; phone ⇒ `type="tel"`; decimal amount may use `inputmode="decimal"` with locale-aware parsing. `inputmode` is a keyboard hint, not validation.
- **M · [Autofill][autofill]:** user-data fields expose purpose-matched tokens: `name`, `email`, `street-address`, `current-password`, `new-password`, `one-time-code`; e.g. `<input type="password" name="password" autocomplete="current-password">`. No blanket autocomplete ban. Username/email/code ⇒ selective `spellcheck="false"`, often `autocapitalize="none"`; prose retains useful correction. Search fields use search-specific names, not password-like names; `autocomplete="off"` only where inappropriate autofill warrants it, not as a security boundary.
- **M · Input integrity:** paste/password managers/OTP autofill work; no paste blocking or keystroke censorship. Hydration/re-render never discards value, selection, or focus; stable keys and component identity; controlled inputs update synchronously and never accidentally switch controlled/uncontrolled. Text-expansion whitespace is normalized only when semantically ignorable; passwords/code/significant spaces remain untouched. Native `<select>` foreground/background remain readable in every supported theme; explicitly set both where platform rendering needs them.

## 4. Validation, submission, mutations

- **D · [Validation flow][validation]:** submit remains available before validation; incomplete submission reveals actionable errors. `required`, correct types, and other native constraints cover simple rules; server validates independently. Temporary invalid text is editable; validation explains instead of silently rejecting keys. Errors sit beside fields; failed submit focuses first invalid field or an appropriate linked error summary; other entered values survive.
- **M · In-flight state:** pending submission ⇒ disable submit or enforce `aria-disabled="true"` with an activation guard when retaining focus is necessary; expose busy state, preserve button dimensions/original label, add spinner; completion ⇒ restore usable control and meaningful focus. Server-side deduplication/idempotency protects retriable non-idempotent writes; the same logical retry reuses its key, a new operation gets a new key. Disabled controls are not submitted, so required request data cannot depend on disabled fields being serialized.
- **D · Local state:** immediate-setting switch takes effect immediately, with pending/error/revert feedback if persistence fails; staged multi-field choices use a form/checkbox pattern rather than a misleading immediate switch. Likely-success, reversible mutation ⇒ optimistic UI, server reconciliation, failure explanation plus rollback/Undo; irreversible or high-risk operations do not fake success.
- **M · Destruction:** recoverable routine deletion ⇒ Undo or recoverable trash, not repetitive confirmation; irreversible/unusual destruction ⇒ explicit consequence and action-specific confirmation. Retriable failure ⇒ retained work plus Retry; cancel ⇒ predictable outcome; dirty navigation ⇒ autosaved recovery or a loss warning where unsaved data would actually disappear.
- **D · Examples/help:** inline help precedes tooltips. Placeholder shows a plausible format, e.g. `name@example.com`, `+49 151 23456789`, `sk-example…`; Open-ended entry hints may end `…`; literal format examples do not acquire misleading punctuation. Error copy identifies the actual problem and next step, not generic “Invalid” or false reassurance.

## 5. Loading, progress, feedback

- **D · Pending indicators:** avoid flash with tunable display delay `150–300ms`; once shown, a brief `300–500ms` transition/display budget may reduce flicker. These are heuristics, not universal latency rules; completed work is never falsely presented as ongoing and useful interaction is not delayed. A suspense/loading boundary alone does not guarantee these timings; implement/test the desired policy explicitly. Skeleton geometry reserves final dimensions, not arbitrary gray blocks.
- **M · Progress:** measurable completion ⇒ determinate progress with accurate fraction; unknown completion ⇒ indeterminate activity; newly measurable ⇒ switch to determinate. No invented percentage, backward-running estimate, or fake near-complete stall; stalled work explains its status and provides cancellation/retry where meaningful. Persistent instructions/errors remain until resolved or dismissed, not until an arbitrary toast timeout.
- **D · Local feedback:** outcome appears beside its trigger: Copy ⇒ temporary inline check plus accessible “Copied”; invalid field ⇒ associated inline explanation; ongoing operation ⇒ nearby status. Global toast only for genuinely global/background events. Processing labels may use `Saving…`; no layout jump when indicators appear.
- **M · [Announcements][status]:** status updates use `role="status"`/`aria-live="polite"`; urgent interruption uses alert semantics sparingly. No duplicate announcements, per-keystroke live-region noise, or focus stealing for routine completion; loading regions expose meaningful busy state.

## 6. Navigation, state, recovery

- **M · Shareable state:** meaningful filters, tab, page, sort, selected record, and useful expanded panels serialize into URL/search params; refresh/share/Back/Forward reconstruct the view. Secrets, private form values, hover, animation progress, and every incidental `useState` do not belong in URLs.
- **M · [History][history]:** navigation uses genuine history semantics; Back/Forward restores route state and prior scroll; replacing versus pushing history reflects whether a meaningful navigation occurred. Anchor links use stable IDs and sticky-header offset, e.g. `scroll-margin-top:calc(var(--header-h) + 1rem)`; optional smooth scrolling becomes instant under reduced motion.
- **D · Authentication:** where a server exists, protected-route checks/redirects happen before protected content renders, not after a client flash; return destination is retained safely. Client routing is not authorization. Draft preservation and auth expiry handling prevent silent work loss.
- **M · State coverage:** every view has intentional initial/loading/empty/sparse/dense/success/error/offline/permission-denied states where applicable. Empty collection ⇒ relevant creation/import action, optionally template; empty search ⇒ clear filters/change query; failure ⇒ recovery path. No inaccessible disabled dead end.
- **D · Navigation controls:** tab bars represent peer destinations, not commands; actions belong in toolbars/buttons. Tab identities remain stable across navigation; empty destinations stay understandable rather than disappearing or becoming unexplained disabled tabs. Familiar platform navigation is preferred over gratuitous custom conventions.

## 7. Menus, tooltips, dialogs

- **M · [Tooltips][tooltip]:** essential help/disabled-state reasons remain available without hover. Native disabled buttons are not keyboard-focusable, so their tooltip cannot be the only explanation. Tooltip content is noninteractive; links/forms require a popover/dialog. Hover/focus content is dismissible, hoverable, and persistent as required; trigger is associated with description; Escape dismisses without losing context.
- **D · Pointer menus:** first tooltip in a group waits; subsequent peers may appear immediately. Nested menus tolerate diagonal travel with a prediction cone/safe polygon. Pointerdown opening is optional, with cancellation/release handling and keyboard parity; the opening release cannot accidentally select an item; destructive actions never execute merely because a pointer went down. Menu item with further required input may use `Rename…`.
- **D · Modality:** modal presentation requires a focused task or important decision; unrelated browsing remains outside. Dismissal is obvious; existing work/context survives; no nested “app inside a modal” navigation. Scrolling modal/drawer may use `overscroll-behavior:contain` without destroying necessary scrolling or focus visibility.
- **D · Alerts:** essential, actionable interruptions only; routine updates/offline startup use contextual feedback/cached content. Alert = specific title, necessary consequence, ≤3 clear actions. Irreversible action includes Cancel; destructive action is not the default. A risky choice may have no default. Escape follows platform cancellation behavior. Initial safe focus and default activation remain distinct; opening a dialog never transfers the triggering keystroke into confirmation.
- **D · Buttons:** custom buttons expose pressed feedback; a view usually has 1 primary action, at most 2 when both are genuinely primary. Related controls share size rules; prominence comes from hierarchy/style, not arbitrary enlargement. Familiar icons retain familiar meanings. Primary, secondary, cancel, and destructive roles remain distinct; danger is not color-only.

## 8. Typography, scaling, text fit

- **M · Text resilience ([reflow][reflow], [spacing][text-spacing]):** 200% text enlargement remains usable; 320px-wide reflow/400% desktop zoom avoids two-dimensional scrolling except genuinely two-dimensional content. User spacing overrides do not lose content/function: line-height `1.5×`, paragraph spacing `2×`, letter spacing `.12em`, word spacing `.16em`. These are robustness tests, not mandatory authored typography values.
- **D · Type system:** limited families; clear hierarchy; ordinary small text defaults to weight ≥400, medium headings approximately 500–600. These are contextual preferences, not font-independent laws. Hover/selection must not change glyph metrics and shift neighbors; stable-metric alternatives are acceptable. Numeric comparison/timers ⇒ `font-variant-numeric:tabular-nums` or suitable monospace.
- **D · Fluid type:** bounded, accessible sizing, e.g. `font-size:clamp(3rem,2rem + 2.5vw,4.5rem)`; `clamp(48px,5vw,72px)` is a visual example, not an accessibility guarantee. Verify zoom enlargement despite clamp limits. `-webkit-text-size-adjust:100%` may control mobile landscape text inflation; it never substitutes for zoom/scaling tests.
- **M · User text settings:** text containers expand with content; fixed heights do not clip scaled labels. Large text reflows horizontal groups vertically where needed. Custom fonts preserve character coverage and readable weight. Browser font preferences and supported text-size/contrast settings remain effective; smaller type does not solve an overcrowded layout.
- **O · Rendering/detail:** `-webkit-font-smoothing:antialiased` and `text-rendering:optimizeLegibility` are tested rendering choices, not universal legibility improvements. Prose may use curly quotes; code retains literal punctuation. Rag, widows, and orphans get deliberate wrapping without breaking responsive layouts. Readable `::selection` covers ordinary and gradient text; gradient selection replaces transparent fill, e.g. `-webkit-text-fill-color:HighlightText;background:Highlight;color:HighlightText` with platform testing.

## 9. Layout, spacing, safe areas

- **M · Responsive layout:** intrinsic sizing/Flexbox/Grid handle flow before JavaScript measurement. Narrow phone, laptop, wide monitor, portrait/landscape, zoom, localization, and very long user content remain usable. `min-width:0`, wrapping, and constrained media solve actual overflow; no blanket `overflow-x:hidden` concealing inaccessible content. Scrollbars remain available when useful; Test with always-visible scrollbars; use `scrollbar-gutter:stable` when scrollbar appearance would shift the layout.
- **M · Insets/occlusion:** important content respects safe areas, toolbars, browser chrome, and on-screen keyboards; edge-to-edge layouts account for `env(safe-area-inset-*)`, e.g. `padding-bottom:calc(1rem + env(safe-area-inset-bottom))`. Focused controls and submit actions remain reachable with the keyboard visible.
- **D · Alignment:** every element has an intentional grid/baseline/edge/optical relationship; documented ±1px optical adjustments are valid. Icon/text lockups balance stroke, weight, dimensions, gap, and contrast. Repeated components share spacing rules rather than unrelated magic numbers. 50% browser zoom is a useful ultrawide stress test, not a substitute for real viewports.
- **D · Containers:** nested corners are concentric where intended: inner radius approximately `max(0,outer radius − inset)`, e.g. `16 − 4 = 12px`; child radius ≤ parent. Skeletons, media, loading controls, and asynchronously inserted content preserve expected geometry.

## 10. Contrast, themes, visual surfaces

- **M · [APCA text contrast][apca]:** APCA guides perceptual text-color decisions; `Lc` is lightness contrast, not a ratio or percentage. Project targets: body text `|Lc| ≥75`, preferably `≥90`; non-body content `≥60` only at sufficient size/weight. Reference-font anchors at `Lc75`: `18px/400`, `16px/500`, `14px/700`; at `Lc60`: `24px/400`, `18px/600`, `16px/700`. Sizes are CSS px; weights require comparable stroke thickness and x-height, not merely the same CSS weight number. Actual font/use case meets the supported size/weight guidance; no blanket `Lc60` pass for small text. These are project readability requirements based on evolving APCA guidance, not WCAG thresholds.
- **M · [APCA verification][apca-testing]:** version-pinned APCA-W3-compatible tooling evaluates supported color-space inputs; non-sRGB colors are converted correctly, not reinterpreted as sRGB channel values. Foreground and actual composited background retain their order; light-on-dark returns negative `Lc`; thresholds compare `Math.abs(Lc)`. Swapping colors requires recalculation. Test every theme/state and the lowest-contrast background beneath text on gradients/images. Evidence records foreground/background, font size/weight, signed `Lc`, target, and tool/version; no unmeasured accessibility claim.
- **M · WCAG contrast ([text][contrast], [UI][nontext-contrast]):** WCAG 2.2 AA text ≥4.5:1; large text ≥3:1, where large = ≥24px regular or ≥18.667px bold; essential UI boundaries/graphics ≥3:1 against adjacent colors. Actual rendered backgrounds, gradients, translucency, hover/focus/selected states are tested. APCA guides readability; WCAG conformance is checked separately. A passing APCA score never excuses a failed required WCAG check.
- **M · Redundancy:** state/error/chart meaning is not color-only; text, shape, pattern, icon, or position carries equivalent meaning. Charts use distinguishable palettes plus labels/legend and accessible information. Interactive states remain obvious; extra contrast is the default, not permission to reduce baseline readability.
- **D · Semantic color:** semantic system colors retain their intended roles and adapt to appearance; no copying a light-mode RGB value as a universal token. Custom palettes cover light/dark × normal/increased contrast; test real bright/dim environments. Color meaning stays consistent and culturally appropriate; noninteractive text does not misleadingly reuse interactive styling.
- **M · Browser theme:** document `color-scheme` matches actual supported/current appearance; native widgets and scrollbars remain legible; `theme-color` follows page chrome/background where supported. Theme changes suppress unrelated hover/layout transitions and do not strand elements in animation states. SVG favicon may use internal `prefers-color-scheme` styling.
- **O · Surface polish:** ambient+directional shadows with ≥2 layers; subtle translucent border plus shadow; hue-related borders/shadows/text on colored surfaces. Expensive blur is not a prerequisite for hierarchy. Dark mask banding ⇒ test a background-image fade; scaled/blurred rectangular glow banding ⇒ test radial gradient. All decoration remains subordinate to contrast and performance.

## 11. Motion

- **M · Purpose/control:** motion explains state, spatial continuity, or deliberate nonessential delight; no animation is the only carrier of information. Input can interrupt/cancel/reverse it. Gesture-linked motion tracks the gesture; origin corresponds to the trigger; entry/exit directions remain coherent. Frequent context-menu openings, routine list edits, and trivial hover do not accumulate gratuitous delay.
- **D · Timing/scale:** common microinteractions default ≤200ms, not every animation universally. Easing follows distance, size, and trigger. Dialog example ⇒ opacity plus scale approximately `.8→1`, not `0→1`; button press ⇒ `1→.96` or approximately `.9`, not `.8`. These are optional proportionality anchors; no scaling is preferable when unnecessary or motion-sensitive.
- **M · Reduced motion ([preference][reduced-motion], [pause controls][pause]):** `prefers-reduced-motion:reduce` removes/replaces nonessential translation, zoom, parallax, and smooth scrolling; state changes remain clear. Default autoplay is avoided; allowed decorative loops are muted/nonessential. Automatically moving content alongside other content lasting >5s, including endlessly repeated short loops, has pause/stop/hide unless essential. Offscreen/hidden-page loops stop consuming animation work.
- **D · Implementation:** CSS first, then WAAPI, then JS animation tools when needed; actual performance wins over library prejudice. Prefer `transform`/`opacity`; layout/paint animation requires measurement. Explicit transition properties only, never `transition:all`. SVG transform example ⇒ `<g>` wrapper with `transform-box:fill-box;transform-origin:center`.
- **M · Layer budget:** large `filter:blur()`/`backdrop-filter` areas and excessive composited layers are profiled. `translateZ(0)`/`will-change` only fix demonstrated issues; enable shortly before/during work, remove afterward. Text-scaling artifacts ⇒ animate a wrapper and test rasterization before forcing GPU layers.

## 12. Runtime, rendering, network

- **M · Measurement:** extension-free profiling; CPU/network throttling; representative Chromium, Gecko, and WebKit browsers plus real touch devices, including battery-saving modes. Actual interaction traces outrank assumptions. Field [Web Vitals][vitals] targets at p75, segmented mobile/desktop: LCP ≤2.5s, INP ≤200ms, CLS ≤.1. These are outcome thresholds, not substitutes for individual-flow tests.
- **D · Mutations:** ordinary POST/PATCH/DELETE targets <500ms end-to-end under documented conditions; long-running work uses truthful progress/background handling. Report network/device/percentile before claiming compliance; no universal promise across arbitrary networks.
- **M · Main thread:** batch geometry reads before writes; no repeated forced read/write layout cycles. Expensive transferable computation ⇒ Web Worker. Large lists ⇒ measured virtualization with focus/keyboard/accessibility preserved; `content-visibility:auto` is a separate offscreen-rendering optimization, not equivalent DOM virtualization.
- **D · Component rendering:** uncontrolled inputs when controlled state adds no value; controlled paths keep keystrokes cheap. A component profiler identifies rerenders before memoization. High-frequency pointer/wheel animation may use refs, requestAnimationFrame, and isolated direct DOM updates instead of per-event component state; framework-owned attributes have no competing writers; cleanup/lifecycle remain correct.
- **M · Capability adaptation:** expensive effects/media adapt to observed support, performance, reduced-motion/data preferences where available, and resource constraints; no unsupported API dependency or coarse device-name assumption. Offscreen mobile videos pause and, when necessary, unload/unmount without losing required user state.

## 13. Images, fonts, video

- **M · [Image semantics][images]:** meaningful image ⇒ `<img>` with contextual `alt`; decorative image ⇒ empty `alt` or decorative CSS; images remain copyable where content use warrants it. HTML/SVG illustration exposes one coherent accessible image name/description, e.g. `role="img" aria-label="…"`, not a noisy decorative subtree. Essential complex information also has a useful textual equivalent.
- **M · Geometry/priority:** image dimensions or aspect ratio reserve space; responsive `srcset`/`sizes` match rendered size. Actual LCP image is not lazy-loaded; high priority/preload only for measured critical assets, not all visible images. Below-fold images normally lazy-load. Critical external origins may use `<link rel="preconnect" href="https://cdn.example" crossorigin>` with correct CORS requirements.
- **D · Fonts:** required scripts/glyphs only, correctly partitioned via `unicode-range`; needed variable axes only; WOFF2 where suitable. Only critical fonts preload, e.g. `<link rel="preload" href="/ui.woff2" as="font" type="font/woff2" crossorigin>`; loading/fallback metrics avoid invisible critical text and layout shift. Missing subsets never erase translated/user-generated content.
- **D · Animated media:** short decorative animation normally uses efficient video instead of GIF; `<video autoplay muted loop playsinline>` still needs autoplay-failure/static/reduced-motion handling. Meaningful video uses accessible controls. Pause/offscreen/resource behavior is explicit; multiple eager video loops are not free.
- **O · Video-as-image enhancement:** nonessential H.264 MP4 may be offered as `<picture><source type="video/mp4" srcset="/loop.mp4" media="(prefers-reduced-motion:no-preference)"><img src="/still.webp" width="640" height="360" alt=""></picture>`. Supporting browsers may animate; others use the image fallback. This is not universal video support; verify target browsers. Loop >5s still requires a stop/hide mechanism; essential content or playback controls ⇒ `<video>`, not image-pipeline animation.

## 14. Content, localization, accessible media

- **M · Language ([locale formatting][intl]):** explicit user preference precedes `Accept-Language`/`navigator.languages`; IP/GPS does not decide language. Dates/times/numbers/currencies use locale-aware formatters such as `Intl.DateTimeFormat`/`Intl.NumberFormat`, including actual currency precision and user time zone. Long translations, non-Latin scripts, RTL where supported, and short/long user content retain hierarchy and access.
- **M · Literal tokens:** selected names/code/identifiers that must remain verbatim use `translate="no"`; no blanket exclusion of translatable prose. Nonbreaking glue is intentional: `10&nbsp;MB`, `⌘&nbsp;+&nbsp;K`; `&#x2060;` prevents a break without adding visible space. UI ellipsis uses `…`; literal code is not typographically rewritten.
- **M · Media access:** speech and meaningful sounds have captions; audio-only content has transcript; essential visual information has appropriate description/text alternative; media controls work with keyboard and assistive technology. Decorative media stays out of the accessibility tree. Sound/haptics/color/motion never provide the only essential notification.
- **M · [Translation structure][i18n]:** the document has the correct `lang`; language changes have local `lang` where needed. Direction uses `dir`; layout uses logical properties such as `margin-inline-start`, not hard-coded left/right assumptions. Whole messages are translated with placeholders and plural rules; no sentence assembly from separately translated fragments. Untrusted/mixed-direction identifiers use isolation such as `<bdi>`; truncation never hides the only accessible value or action.
- **D · Content availability:** essential labels, instructions, errors, and results remain available without hover or timed disclosure. Truncation has an accessible route to the full content; meaningful text remains selectable/copyable. Copy controls return the underlying value, not the shortened display.

## 15. Language and interface copy

- **D · Plain technical English:** familiar words, active voice, concrete verbs, one term per concept. `use`, not `utilize`; `start`, not `initiate`; `Save changes`, not `Perform a save operation`. Preserve precise domain terms when simpler words change meaning; explain unfamiliar terms once. Distinguish different operations: `delete` destroys an object; `remove` detaches it from a collection. No synonym rotation, idioms, marketing claims, jokes, blame, or unexplained abbreviations. These rules adapt selected [controlled-language principles][ste] for interface copy.
- **D · Instructions:** one action per sentence; actor/condition explicit when relevant; condition before action: `To export the report, select Download CSV.` Prefer `Select Save` to device-specific `Click Save`/`Tap Save`. Use positive conditions: `Send notifications` instead of `Do not disable notifications`. Place warnings before risky actions. Aim for ≤20 words per instruction sentence; retain articles, units, conditions, and necessary safety detail. Shorter text is not better when it becomes ambiguous.
- **M · Labels ([accessible names][label-in-name]):** action button = imperative verb + necessary object: `Create project`, `Save changes`, `Copy link`, `Download CSV`, `Delete account`. Navigation/tab = destination: `Settings`, `Members`; stable toggle label = controlled property: `Email notifications`. Icon-only controls use equally specific accessible names; visible labels remain in accessible names. `Continue` is appropriate only for an actual next step; `OK`/`Yes`/`Submit` never conceal a consequential action. Confirmation repeats the action, e.g. `Delete account?` + `Delete account` / `Cancel`.
- **M · [Feedback][error-suggestion]:** failure identifies the failed operation, known cause, and available recovery without inventing a diagnosis. Unknown cause ⇒ `Upload failed. Try again.` Known size limit ⇒ `File exceeds 10 MB. Choose a file of 10 MB or less.` Preserve work; state recovery only when it exists. Action label remains `Save`; adjacent status progresses `Saving…` → `Saved`. Results appear only when confirmed; pending status appears only while pending. Routine success needs no extra sentence. Warnings name the affected object, consequence, and reversibility: `Delete “Draft”? You cannot undo this action.`
- **D · Brevity and form:** sentence case for headings, controls, labels, and errors; retain acronym/proper-name casing. Button labels usually 1–4 words, but specificity wins over word count. No final period on short labels; complete messages use normal punctuation. Use `and`, not `&`, unless part of an established term. Remove `please`, `simply`, `just`, `successfully`, and `in order to` when they add no meaning. Exact names, code, and units remain literal; counts use digits and locale-correct plurals. `…` means pending work or required further input, not decorative truncation of instructions.

## 16. Implementation: StyleX, TypeScript, Vite+

### StyleX

- **M · Existing system:** existing components/tokens are the baseline; no parallel styling system, arbitrary replacement palette, or framework migration. Component styles use `stylex.create`; application uses `stylex.props`. Raw CSS above is behavioral reference, not a request for separate component stylesheets. Global CSS stays limited to deliberate document defaults, resets, font declarations, and documented integration requirements.
- **M · [Compilation][stylex-defining]:** style definitions are statically analyzable, preferably module-scoped. No arbitrary imported objects/helper calls or object-spread composition inside raw style definitions. Pseudo-classes/media conditions nest under properties and include `default`, e.g. `opacity:{default:1,':disabled':0.5}`; `default:null` means no default declaration. Disabled opacity is an example, not a universal contrast-safe treatment. Finite states use static variants; genuinely runtime values use typed dynamic styles, e.g. `width:(value:number)=>({width:value})`.
- **M · [Composition][stylex-using]:** `stylex.props(styles.base,styles[variant],disabled && styles.disabled)` merges styles; do not concatenate generated classes or spread compiled style objects. Later values win for the same property; shorthand/longhand conflicts depend on `styleResolution`, so prefer consistent longhands. Hover conditions use `@media (hover:hover)`; focus-visible, pressed, invalid, disabled, reduced-motion, and forced-color states remain explicit. Generated class names are not stable test selectors.
- **M · [Tokens][stylex-vars] and [themes][stylex-themes]:** named `stylex.defineVars` exports live in `*.stylex.ts` and are imported directly from their defining module. Shared semantic tokens cover text, surfaces, borders, focus, spacing, type, radii, and motion; repeated values reuse tokens, not copied literals. `stylex.createTheme` overrides token groups for a subtree. No theme-specific colors scattered through components; no accessing token values as runtime measurements. Logical properties preserve directionality; nested-corner and spacing relationships stay explicit.

### TypeScript

- **M · [Strict checks][ts-strict]:** `strict:true`, [`noUncheckedIndexedAccess:true`][ts-indexed], [`exactOptionalPropertyTypes:true`][ts-optional]; no strict-family override to `false`, including [`useUnknownInCatchVariables`][ts-catch]. Existing stronger checks stay enabled. No diagnostic suppression, skipped check, or relaxed lint/tsconfig rule to make failing code pass. Replace unsafe assertions with validated narrowing; `as unknown as T`, `value!`, and `field!:T` are not fixes.
- **M · Precise types and [narrowing][ts-narrowing]:** boundary input starts as `unknown`; validate API/JSON, URL, storage, environment, form, file, and message input before use. Check structure and domain constraints; invalid input yields an explicit error, not a cast or invented default. Declared types/generics do not validate runtime data. Conditions express intent: `value === undefined`, `value === null`, `text.length > 0`; `if(flag)` requires `flag:boolean`. Missing-value fallback uses `??`, not `||`, when `0`, `false`, or `''` is valid.
- **M · Errors:** caught values remain `unknown` until narrowed, e.g. `error instanceof Error`. Recover explicitly or propagate with the original cause; no empty catches, fabricated success, or log-and-continue after failure. Await/return promises or attach deliberate rejection handling; discarding a promise is not error handling. Expected cancellation receives explicit treatment, not a blanket catch.
- **M · [State models][ts-narrowing] and ownership:** variants use literal unions, e.g. `type Tone='primary'|'secondary'|'danger'`; async states use discriminated unions, e.g. `{status:'pending'}` or `{status:'success';data:T}`. Impossible combinations are unrepresentable; failure carries recovery data; absence ≠ empty success. Exhaustive branches use checked `never`, not `as never`. Shared values are immutable; updates produce new values; mutable defaults are fresh per call/instance, including nested members. Iteration derives a new collection without mutating the source or its elements. Props preserve native semantics, refs, labels, precise event types, and focus/disabled/busy behavior.
- **M · [Numeric correctness][float-comparison]:** no exact floating-point equality. For finite, range-checked operands, compare with domain-derived absolute/relative tolerances: `Math.abs(a-b) <= Math.max(absTol,relTol*Math.max(Math.abs(a),Math.abs(b)))`; tolerances are finite, nonnegative, and appropriate to the units/magnitude. `Number.EPSILON` is not a universal tolerance. Exact decimal domains use decimal arithmetic or safely ranged integer units; validated safe-integer IDs/counts retain exact equality.

### Vite+

- **M · Configuration:** use the installed versions, lockfile, and existing `vite.config.ts`; `defineConfig` comes from `vite-plus`. Style compilation runs in development, tests, and production. With [`@stylexjs/unplugin`][stylex-plugin], `stylex.vite()` precedes the relevant framework plugin; a CSS entry and the documented development CSS-loading path remain wired. Verify emitted CSS and style updates; a successful JavaScript build alone does not prove styles loaded.
- **M · Checks:** [`vp check`][vp-check] covers formatting/linting; type checking requires `lint.options.typeCheck:true` and the appropriate type-aware setup, normally `typeAware:true`. [`vp test`][vp-test] runs the built-in test runner; [`vp build`][vp-build] builds the application. Custom package scripts use [`vp run <script>`][vp-run]; built-in commands do not implicitly run same-named scripts. Use the repository’s configured commands without silently changing tools or disabling checks.
- **M · Interface verification:** changed interactions have behavioral tests for role/name, keyboard/focus, state transitions, validation, and recovery. Automated tests do not replace browser checks for touch, zoom/reflow, long/translated text, themes/contrast, reduced motion, slow/offline operation, and real-device behavior. Check the production build as well as development; test data and screenshots cover actual component states, not only the default appearance.
